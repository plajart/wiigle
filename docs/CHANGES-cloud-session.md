## 0. 용어 체계 (최신 — 이 문서 전체에 적용)

| 계정 `role` | 부르는 이름 | 범위 | 관리모드(경로) |
|---|---|---|---|
| `owner` | **본사** (소유자) | 플랫폼 전체 | 본사 관리모드 (`/owner`) |
| `admin` | **고객사** (운영자) | 한 고객사 | 고객사 관리모드 (`/hq`) |
| `manager` | **매장** (관리자) | 한 매장 | 매장 관리모드 (`/store`) |
| `user` | **고객** | 본인 | 고객 모드 (`/me`) |

- 계층: 본사 > 고객사 > 매장 > 고객. `role` 값, DB 필드(`companyAdminOf`, `storeManagerOf`), URL 경로(`/owner`, `/hq`, `/store`, `/me`)는 **바꾸지 않았다**(화면·문서의 이름만 바뀜)
- **의미가 뒤바뀐 말 주의:** 예전에는 "본사"가 고객사(회사)를, "소유자"가 플랫폼 운영자를 뜻했다. 이제 **"본사" = 소유자(플랫폼)**, 회사는 **"고객사"**다. 그래서 예전 표현은 이렇게 읽는다 — "본사 관리모드/본사 운영자" → **고객사 관리모드/고객사 운영자**, "소유자 관리모드" → **본사 관리모드**, "고객사(본사)" → **고객사**, "본사 포인트/본사 지급분" → **통합포인트/고객사가 지급한 통합포인트**
- 이 문서의 5-5 이후 절은 위 새 용어로 정리했다. 그 이전 절의 "소유자"는 그대로 **본사(소유자)** 를 뜻한다
- 통합포인트 = 고객사 단위로 운영되는 포인트(고객사가 지급한 분 + 그 고객사 매장들의 적립분을 같은 고객사 안에서 합쳐 쓴다). "본사 포인트/매장 포인트"라는 말은 화면에서 쓰지 않는다

## 1. 배포 절차 (순서 중요)

1. **DB 백업**
2. 코드 pull → `npm ci` → `npm run build`
3. **마이그레이션 실행** — `scripts/migrate-to-multitenant.ts` (작성만 했고 실행은 안 함)
   ```bash
   MONGODB_URI="..." npx tsx scripts/migrate-to-multitenant.ts           # 미리보기(기본)
   MONGODB_URI="..." npx tsx scripts/migrate-to-multitenant.ts --apply   # 반영
   ```
   - 더파티·반들한식뷔페 Company 생성, 기존 매장에 companyId 부여, `isHqAdmin:true` → `role:"owner"`, `storeAdminOf` → `role:"manager"`+`storeManagerOf`.
   - 멱등. 옛 필드(`isHqAdmin`, `storeAdminOf`)는 지우지 않는다.
3-0. **통합포인트 고객사 분리 마이그레이션** — `scripts/migrate-company-points.ts`. **새 앱을 시작하기 전에** 실행(옛 유니크 인덱스를 지운다). 통합포인트 잔액이 있으면 `--assign-hq-to="고객사"` 필요. 아래 5-7 참고
3-1. **이전 손님 계정에 임의 초기 비밀번호 부여** — `scripts/issue-initial-passwords.ts`(미리보기 → `--apply`). 아래 5-3 참고
3-2. **운영 계정 정리** — `scripts/setup-accounts.ts`(미리보기 → `--apply`, `FIXED_PASSWORD` 환경변수 필요). 아래 5-6 참고
   - 미리보기에서 "고객사가 없는 매장 N개" 경고가 나오면 수동 지정 필요(`companyId`는 필수).
4. 서버 재시작 (권한 체계·등록 방식이 바뀌었으므로)
5. 모든 사용자는 **재로그인** 필요(세션이 JWT라 role 변경이 즉시 반영되지 않음)

### 환경변수
| 이름 | 용도 |
|---|---|

| `SMS_WEBHOOK_TOKEN` | **신규, 선택.** 있으면 `Authorization: Bearer` 로 전송 |

## 4. 원샷 설치 (인증코드 없는 포스기 설치)

### 서버
- `lib/models/PosProvisionToken.ts` — 매장별 1회용 설치 토큰. 원문은 저장하지 않고 sha256 해시만 저장, 24시간 TTL
- `app/api/v1/pos-agent/download/route.ts` — 재작성. `requireStoreManager` + `resolveStoreId`(`?storeId=`). 호출마다 토큰을 새로 만들어 `pos-agent-src/*` + `provision.json`을 **즉석 zip**으로 응답
- `lib/zip.ts` — 의존성 없는 zip 생성기(`archiver`는 설치·lock 갱신을 피하려고 쓰지 않음). `package.json` 변경 없음
- `POST /api/v1/pos/agent/register` — `{token, terminalName}` → 토큰을 원자적으로 소모(`findOneAndDelete`) → PosTerminal 생성·apiKey 발급. 매장의 첫 ACTIVE 단말이면 `isPrimary`. IP당 20회/10분 제한
- `GET /api/v1/pos/agent/terminals` — Bearer apiKey 인증, 자기 매장 포스기 목록
- **삭제:** `api/v1/pos/agent/pairing-code`, `api/v1/stores/[storeId]/pos-terminals/pairing-code`, `api/v1/pos/terminals/register`(옛 코드 방식), `lib/models/PosPairingCode.ts`
- `/store/terminals` — "포스기 다운로드" 버튼 + 등록 목록·대표지정·해지·상세로 단순화(코드 발급·LAN 탐색 UI 제거). 사이드바 라벨은 "포스기 다운로드"

### 에이전트 `pos-agent-src/point-terminal-agent.ps1` (617줄 → 약 480줄)
- `provision.json`의 토큰으로 `/api/v1/pos/agent/register` 자동 호출 → `terminal-config.json` 저장 → `provision.json` 삭제
- 등록 직후 `Show-TerminalList` 창으로 포스기 목록 자동 표시, 트레이 메뉴에 "포스기 목록..." 추가
- **제거:** `Read-Host` 코드 입력, `Start-DiscoveryAnnounce/Listener`, `Start-LocalHttpApi`, `Register-PeerByIp`, `$Script:Peers`, 관련 파라미터(`LocalHttpPort`, `DiscoveryUdpPort`, `DiscoveryIntervalSec`)
- **UTF-8 BOM 유지** — Windows PowerShell 5.1이 한글을 읽으려면 필요. 이 파일을 편집할 때 BOM을 잃지 말 것
- 이미 설치된 포스기는 그대로 동작(apiKey 방식 불변). 새 설치만 새 방식

### 동작상 주의
- 받은 zip 하나는 **한 번만** 등록된다. 포스기를 더 추가하려면 그 PC에서 다시 다운로드
- 토큰이 든 zip은 그 매장의 등록 권한을 가지므로 외부 전달 금지(화면에도 안내)

## 5. 비밀번호 찾기 · 변경 (신규)

배경: 일괄 이전으로 만들어진 고객 계정은 무작위 비밀번호(`lib/points.ts`)라 본인이 로그인할 수 없다.

- `lib/sms.ts` — 문자 발송 어댑터. `SMS_WEBHOOK_URL`로 `{to, text}` JSON POST. **실제 문자 업체는 미정** — 업체 API가 이 형식과 다르면 이 파일의 `sendSms`만 교체하면 된다. 미설정 시 발송하지 않고 `false` 반환(코드를 로그·응답에 남기지 않음)
- `lib/models/PasswordReset.ts` — 전화번호당 1건, 인증번호는 **해시로 저장**, 5분 TTL, 틀린 시도 횟수 기록
- `lib/password.ts` — 비밀번호 규칙(8자 이상, 72바이트 이하), 번호 정규화, 해시·비교
- `POST /api/v1/auth/password/forgot` — 가입 여부와 무관하게 항상 같은 응답(번호 존재 노출 방지). 60초 재발송 제한, IP당 10회/10분·번호당 5회/시간
- `POST /api/v1/auth/password/reset` — 인증번호 확인 후 새 비밀번호 설정. 최대 5회 시도, 인증번호 1회용, 성공 시 `phoneVerified=true`. 자동 로그인은 하지 않음
- `POST /api/v1/me/password` — 로그인 회원의 비밀번호 변경(현재 비밀번호 확인 필수)
- 화면: `/forgot-password`(2단계), `/me/password`(사이드바 "비밀번호 변경"), 로그인 화면에 "비밀번호를 잊으셨나요?" 링크·변경 완료 안내
- ~~가입 인증번호 문자 발송~~ → **5-12에서 문자 인증 자체를 없앴다**(가입은 폰번호·비밀번호로 바로 완료). 서버 비밀번호 규칙 검사(8자 이상)는 유지

**중요:** 문자 업체는 비용 문제로 도입하지 않기로 했으므로 `SMS_WEBHOOK_URL`은 비워 둔다(코드는 남아 있어 나중에 연결 가능). 대신 아래 5-1의 **앱 알림**으로 비밀번호 찾기 인증번호를 전달한다. (신규 가입은 문자 인증 없이 바로 가입 — 5-12)

### 5-1. 앱 알림(웹 푸시)으로 인증번호 받기

- `npm install web-push`(+ `-D @types/web-push`) — `package.json`·`package-lock.json` 변경됨. 배포 시 `npm ci` 필요
- `lib/push.ts` — VAPID 설정, `sendPush()`, endpoint **허용 목록**(FCM·Mozilla·Apple·Windows 푸시 도메인만; 클라이언트가 준 URL로 서버가 요청하므로 SSRF 방어). `isPushConfigured()`가 false면 전부 비활성
- `lib/models/PushDevice.ts` — 전화번호에 묶인 기기 구독. 기기(endpoint)는 한 번호에만, 번호당 최대 3대(오래된 것 교체)
- `GET /api/v1/push/public-key` — 브라우저가 구독할 때 쓰는 공개키(미설정 시 503)
- `POST /api/v1/auth/push/register` — 로그인 전 기기 등록. 가입 여부와 무관하게 같은 응답. **`role==="user"`(일반 고객) 번호만 저장**. 이미 다른 기기가 등록돼 있으면 기존 기기들에 "새 기기에서 비밀번호 찾기가 요청되었습니다" 알림 발송. IP당 10회/10분, 번호당 5회/시간
- `POST /api/v1/auth/password/forgot` — 인증번호를 (a) 등록된 기기로 푸시, (b) 문자(설정된 경우)로 발송. 만료된 구독(404/410)은 자동 삭제. **푸시는 일반 고객 계정에만** 발송
- `public/sw.js` — `push`(알림 표시)·`notificationclick`(앱/페이지 열기) 핸들러 추가
- `/forgot-password` — "인증번호 받기" 클릭 시 알림 허용 요청 → 이 기기를 등록 → 인증번호 요청. 알림 거부·미지원이면 안내 문구 표시

**앱 알림 설정**
```bash
node -e "const w=require('web-push');console.log(w.generateVAPIDKeys())"
# 출력된 publicKey / privateKey를 환경변수로:
#   VAPID_PUBLIC_KEY=...  VAPID_PRIVATE_KEY=...  VAPID_SUBJECT=mailto:운영자메일@도메인
```
키는 한 번 정하면 **바꾸지 말 것**(바꾸면 등록된 모든 기기의 구독이 무효가 된다).

**⚠ 보안상 알려진 한계 (의도적으로 수용한 것)**
문자와 달리 앱 알림은 "이 기기가 그 전화번호의 주인이다"를 증명하지 못한다. 로그인 전에 번호만 입력해 기기를 등록하므로, **전화번호를 아는 사람이 자기 폰에서 그 번호의 비밀번호를 재설정할 수 있다**(포인트 탈취 가능). 완화책만 넣었다:
- 소유자·운영자·매장 관리자 계정은 이 방식에서 제외(일반 고객만)
- 기존 등록 기기에 새 기기 등록 알림, 번호당 기기 3대 제한, 요청 횟수 제한, 인증번호 1회용·5회 시도
- 근본 해결은 아니다. 필요하면 다음 중 하나를 추가할 것: 매장 카운터에서 본인확인 후 발급하는 1회용 재설정 QR, 재설정 후 포인트 사용에 추가 확인, 문자 인증 도입

**⚠ 안드로이드 앱(TWA)에서 알림이 뜨려면 (실기기 확인 필요)**
- 현재 배포 중인 APK가 알림 위임(notification delegation)을 켜고 만들어졌는지 확인하지 못했다. 꺼져 있으면 앱 안에서 알림 허용 창이 안 뜨거나 알림이 오지 않을 수 있다. 그 경우 TWA를 재빌드해야 한다(Bubblewrap의 `enableNotifications: true` 등)
- 앱 대신 **크롬 브라우저/홈 화면에 추가한 웹앱**에서는 별도 조치 없이 동작한다(안드로이드). 아이폰은 **홈 화면에 추가한 웹앱**(iOS 16.4+)에서만 웹 푸시가 된다
- 폰의 방해금지·앱 알림 차단 설정이 켜져 있으면 인증번호 알림이 보이지 않는다

## 5-2. 고객사/매장 관리모드 진입 + 현재 위치 표시

요구: 운영자(고객사) 대시보드에서 소속 매장 목록을 보고, 매장을 눌러 **매장 관리자 권한으로** 들어가 관리한다. 운영자 화면 상단에 "어느 고객사", 매장 화면 상단에 "어느 고객사 › 어느 매장"을 항상 표시한다.

- **`GET /api/v1/stores` 범위 제한(보안 수정)** — 예전엔 로그인한 누구나(고객 포함) 모든 고객사의 매장 목록을 받았다. 이제 `requireCompanyAdmin`: 운영자=자기 고객사 매장만, 소유자=전체(또는 `?companyId=`). 응답에 `companyId`·`companyName` 포함
- **`lib/store-context.ts` 재작성** — 소유자·운영자는 `pm_store` 쿠키(httpOnly)에 담긴 "현재 매장"을 쓴다. 쿠키가 없을 때만 `?storeId=` 인정. **매 요청마다** 매장 존재·소속 고객사를 다시 검증(운영자가 다른 고객사 매장 ID로 바꿔도 null). manager는 자기 매장 고정. 내부에서 `dbConnect()` 호출
- **`GET /store/enter?storeId=`** (`app/store/enter/route.ts`) — 소속 확인 후 쿠키 저장·`/store`로 302. 링크는 `<a>`로 걸 것(`next/link` 미리읽기가 쿠키를 바꾸지 않게). 권한 없으면 `/hq`·`/owner`·`/me`로
- **왜 쿠키인가:** 매장 화면 사이드바 링크에 `?storeId=`가 없어서 운영자가 매장 화면 안에서 메뉴를 옮기면 컨텍스트를 잃고 `/me`로 튕겼다. 쿠키로 유지
- **`app/components/ContextBar.tsx` + `globals.css`(`.context-bar`)** — 상단 고정 표시줄(진한 남색, 고객사 칩 › 매장 칩(금색))
  - `/hq`: `고객사 [이름]`(소유자도 들어온 고객사 이름 — 5-5 참고), 고객사 미배정 운영자=빨간 경고
  - `/store`: `고객사 [이름] › 매장 [이름]` + "운영자/소유자가 매장 관리자 권한으로 관리 중" + "← 매장 목록으로"(운영자·소유자만)
- **`/hq` 대시보드** — 소속 매장 목록, 소유자는 고객사별로 묶어서 표시, 각 매장에 "매장 관리모드 열기" 버튼
- **`/store` 레이아웃** — 현재 매장이 없는 소유자·운영자는 `/hq`(`/owner`)로 보냄. "POS 결제 터미널" 메뉴는 manager에게만 표시(운영자·소유자는 `/pos` 접근 불가였음)
- **`/hq/stores`(매장 생성)** — 소유자는 고객사를 선택해야 한다(기존엔 API가 `COMPANY_ID_REQUIRED`를 돌려주는데 화면이 보내지 않아 **소유자는 매장을 만들 수 없었다**). 운영자는 자기 고객사에 자동 생성
- `/hq/vendor` 매장 선택 목록에 고객사 이름 병기(소유자가 여러 고객사를 볼 때)

**주의**
- 운영자/소유자가 매장 관리모드에서 한 작업은 감사로그에 기존 actorType(`STORE_ADMIN`/`HQ_ADMIN`)으로 남는다. "누가(운영자) 어느 매장에서 대신 했는지"를 구분해 남기는 것은 아직 하지 않았다
- `pm_store` 쿠키는 로그아웃해도 브라우저에 남지만, 세션이 없으면 쓰이지 않고 다른 계정으로 로그인해도 매 요청 권한 검증을 거친다
- 로그인 이후 화면(레이아웃·대시보드·진입 흐름)은 DB가 없어 실행해 보지 못했다. 빌드·타입체크와 비로그인 접근 제어(302/307)만 확인

## 5-3. 손님 계정: 임의 초기 비밀번호 부여 → 웹 첫 로그인에서 안내 → 로그인 후 변경

> 이 절은 처음에 "비밀번호를 비워두는" 방식으로 만들었다가 **임의 비밀번호를 부여하는 방식으로 교체**한 최종 내용이다. 빈 비밀번호(`passwordHash=""`)·`pwUnset`·`PASSWORD_SETUP_REQUIRED`는 모두 제거됐다(코드에 남아 있지 않다).

배경: 일괄 이전·POS 적립으로 만들어진 손님 계정은 본인이 비밀번호를 알 수 없어 고객 화면에 로그인할 수 없었다(적립·사용은 계산원이 전화번호로 처리하므로 문제없지만, 포인트 조회는 로그인이 필요).

**흐름**
1. **계정 생성 시 임의 초기 비밀번호 부여** — 포스기 초기화(일괄 이전)와, 계산원이 적립하려고 전화번호를 확인할 때 첫 고객이면(`getOrCreateUserByPhone`) 8자 임의 비밀번호(대문자+숫자, 헷갈리는 글자 제외)를 만든다. 로그인 검증용 `passwordHash`와 안내용 원문 `initialPassword`, 그리고 `firstLogin: true`를 저장한다(`lib/initial-password.ts`)
2. **웹 로그인 화면** — "처음 로그인하시나요? 초기 비밀번호 확인" 링크(전화번호 입력 후) → `POST /api/v1/auth/initial-password`가 그 번호의 초기 비밀번호를 알려주고 비밀번호 칸에 채워준다. **일반 고객(role=user) 계정만** 대상이며 소유자·운영자·매장 관리자의 비밀번호는 어떤 경우에도 알려주지 않는다. IP당 15회/10분, 번호당 5회/시간 제한
3. **로그인 성공** — 서버가 `initialPassword`를 DB에서 지우고 `firstLogin=false`로 바꾼다(**그 뒤로는 어디에도 비밀번호를 안내하지 않는다**). 응답의 `firstLogin:true`로 이번 한 번만 `/me/password`(비밀번호 변경 안내)로 보낸다. 안내 화면에는 "나중에 변경" 링크가 있다(강제 아님)
4. **비밀번호 변경** — `POST /api/v1/me/password`. 초기·임시 비밀번호로 **방금(1시간 이내) 첫 로그인한 세션(`fl`)은 현재 비밀번호 입력을 생략**, 그 외에는 현재 비밀번호 확인 필수. 변경 후 `initialPassword` 폐기·새 세션 발급. 비밀번호 찾기로 재설정해도 폐기
- 영수증 QR로 들어온 손님(`pendingClaimToken`)은 안내 화면을 마친 뒤 그 연결 화면으로 이어진다
- 가입 화면: 이미 등록된 번호면 "처음 로그인하시나요? 초기 비밀번호 확인"을 안내

**"유사한 경우"도 같은 방식**
- 소유자/운영자가 **새 사람을 지정하면서 계정을 만들 때**(`lib/account-assign.ts`)도 임의 임시 비밀번호를 부여하고 `firstLogin: true`로 둔다. 단 **권한 계정(운영자·매장 관리자)의 비밀번호는 로그인 화면에 공개하지 않고, 지정한 사람에게만 한 번 보여준다**(지정한 사람이 본인에게 전달 → 본인은 로그인 후 변경 안내를 한 번 받는다). 손님 계정이 권한 계정으로 승격되면 `initialPassword`를 지운다
- 매장 가입 신청 승인·최초 소유자 생성(`bootstrap`)은 신청자가 직접 정한 비밀번호를 쓰므로 해당 없음

**기존 DB의 이전 계정 처리 — `scripts/issue-initial-passwords.ts`(작성만, 실행은 운영 서버에서 사람이):** 기본 미리보기, `--apply`로 반영. 대상은 `role==="user"` + `name==="포인트 손님"` + `phoneVerified!==true` + 아직 `initialPassword`가 없는 계정. 여러 번 실행해도 안전, 본인이 가입했거나 비밀번호를 재설정한 계정·권한 계정은 건드리지 않는다. **미리보기에서 대상 수가 예상과 맞는지 먼저 확인할 것**

**⚠ 보안상 알려진 한계 (요청에 따라 의도적으로 수용)**
로그인 화면이 초기 비밀번호를 알려주므로, **그 전화번호를 아는 사람은 누구나 초기 비밀번호를 보고 먼저 로그인해 비밀번호를 바꿀 수 있다**(그러면 그 사람이 계정을 차지하고 정당한 손님은 비밀번호 찾기가 필요). 신원 근거가 전화번호뿐이라는 기존 설계와 같은 수준의 위험이다. 완화: 일반 고객 계정만, 요청 횟수 제한, 첫 로그인 성공 즉시 원문 삭제. 근본 대책이 필요하면 매장 카운터에서 발급하는 1회용 설정 링크 등을 검토할 것. 또한 `initialPassword` 원문이 DB에 저장되므로(첫 로그인 전까지) DB 접근 권한 관리에 유의

## 5-4. 적립 비율 설정 제거

적립 비율은 포스기 프로그램에서 관리하므로 이 프로그램에서는 설정·계산하지 않는다.

- `Store.pointPolicy`(earnRate) **필드 삭제**. 이미 DB에 저장된 값은 남지만 코드가 읽지 않는다(정리 불필요)
- `/store/consent`의 "적립률" 카드와 `PUT/GET .../pos-integration/scopes`의 `earnRate`·`pointPolicy` 제거(감사로그 meta에서도 제거). 동의 항목 문구 "결제금액 기준 적립" → "적립 처리"
- **카운터 수동 적립(`POST /api/v1/pos/earn`, `/pos` 화면)**: 결제금액×비율 계산을 없애고 **적립할 포인트를 직접 입력**하는 방식으로 변경. 요청 필드 `saleAmount` → **`earnAmount`**(포인트). 화면에 "포스기 프로그램이 자동 적립하지 못한 경우의 보조 기능" 안내. 정상 경로(포스기 에이전트 → `posAgentEarn`)는 원래 포스가 계산한 적립액을 그대로 반영하므로 영향 없음
- **구 벤더 동기화(`applyVendorSync`, `POST /api/v1/pos/vendor-sync`)**: 비율로 계산하던 `PAYMENT` 이벤트 타입 삭제. 알 수 없는 타입은 이제 **무시**된다(예전 else 분기가 "사용"으로 처리하던 것을 `USE`만 명시적으로 처리하도록 바꿔 오인 차감 방지). 현재 에이전트(`point-terminal-agent.ps1`)는 이 경로를 쓰지 않는다

## 5-5. 본사 → 고객사 관리모드 → 매장 관리모드 (3단계 진입)

요구: 슈퍼관리자인 소유자는 운영자·매장 관리자 권한을 모두 갖는다. 소유자 대시보드에서 고객사 목록을 보고 클릭해 고객사 관리모드로 들어가고, 고객사 관리모드 대시보드에서는 그 고객사의 매장 목록이 나오며 클릭하면 매장 관리모드로 들어간다.

- **`pm_company` 쿠키 + `lib/company-context.ts`** — `resolveCompanyId(session)`: 운영자=자기 고객사, 소유자=고객사 관리모드에 들어간 고객사(쿠키, 존재 여부 매번 재확인). 매장의 `pm_store` 쿠키와 같은 방식
- **`GET /hq/enter?companyId=`** (`app/hq/enter/route.ts`) — 소유자만. 고객사 확인 후 쿠키 저장·`/hq`로 302. 링크는 `<a>`로 걸 것
- **소유자 대시보드 `/owner`** — 고객사 목록의 각 행에 "고객사 관리모드 열기" 버튼(+ 기존 이름 변경)
- **`/hq` 레이아웃** — 소유자가 고객사를 고르지 않고 오면 `/owner`로 보냄. 상단 표시줄에 항상 `고객사 [이름]`(소유자는 "소유자가 운영자 권한으로 관리 중" + "← 고객사 목록으로")
- **`/hq` 대시보드** — 소유자도 들어온 고객사 **하나**의 매장 목록만 보임(예전엔 전체를 고객사별로 묶어서 보여줌). 각 매장 "매장 관리모드 열기" → `/store/enter`
- **`/store/enter`** — 소유자가 매장에 들어가면 그 매장의 고객사도 `pm_company`로 맞춘다("← 매장 목록으로"가 같은 고객사로 돌아가게)
- **`GET/POST /api/v1/stores`** — 소유자의 범위: `?companyId=` → 현재 고객사 관리모드 고객사 → (둘 다 없으면) 전체. 매장 생성은 현재 고객사에 자동(그래서 `/hq/stores`의 고객사 선택 칸 제거)
- **소유자에게 매장 관리자 권한 전부 부여** — `requireOwnStore()`(POS 결제·조회·카드연결·QR 발급 라우트 6개가 사용)가 소유자일 때 **들어가 있는 매장**을 "내 매장"으로 취급한다(권한은 매번 재검증). `/pos` 화면도 소유자는 매장에 들어가 있으면 열린다. **운영자(admin)는 결제 같은 매장 운영 동작은 하지 않는다**(설정·조회만) — 의도적으로 소유자에게만 부여
- **`/hq/applications` → `/owner/applications`로 이동**(소유자 전용이라 고객사 컨텍스트가 필요한 `/hq` 아래에 둘 수 없음). API(`/api/v1/hq/store-applications`)는 그대로
- 소유자 화면에서 "운영자 모드" 바로가기 제거(고객사를 골라 들어가야 하므로). 운영자 사이드바 "포인트 관리" → "통합포인트 관리"(용어 규칙)

**주의**
- 소유자가 매장 관리모드에서 한 결제·적립 등은 감사로그에 그 소유자의 ID로 남는다. "소유자가 대신 처리"한 것을 별도 표시하지는 않는다
- 로그인 이후 화면·진입 흐름은 DB가 없어 실행해 보지 못했다(빌드·타입체크, 비로그인 접근 제어만 확인)

## 5-6. 계정 구조 정리 · 고객사 운영자/매장 관리자 지정 · 논리 검토

### 계정 등급과 권한 흐름 (확정)
| 등급 | 범위 | 하는 일 |
|---|---|---|
| 본사(owner, 소유자) | 플랫폼 전체 | 고객사 생성·이름변경, **고객사 운영자 지정/해제**, 고객사·매장 관리모드 진입(운영자+매장 관리자 권한 전부, POS 결제 포함), 매장 가입 신청 승인, 고객앱 버전 |
| 고객사(admin, 운영자) | 자기 고객사 | **매장 등록, 매장 관리자 지정/해제**, 소속 매장 관리모드 진입(설정·조회, 결제는 안 함), 고객 조회·통합포인트 |
| 매장(manager, 관리자) | 자기 매장 | 매장 설정·POS 결제·포스기 다운로드 |
| 고객(user) | 본인 | 포인트 조회, 비밀번호 |

한 계정은 한 등급만 갖는다. **더파티 시청점처럼 매장은 관리자 계정 없이 정보만 존재할 수 있다.**

### 코드 변경
- **매장 등록에서 관리자 필수 제거** — `POST /api/v1/stores`는 `name`만 필수. `adminPhone`(+`adminName`)을 주면 그 사람을 지정하고, 지정이 실패해도 매장은 남는다(응답의 `managerError`)
- **매장 관리자 지정/해제** — `GET/POST/DELETE /api/v1/stores/[storeId]/managers`(운영자=자기 고객사 매장만, 소유자=전체, `assertStoreScope`). 같은 매장에 여러 명 가능. 이미 가입한 회원이면 승격, 가입 안 한 번호면 `name`을 받아 계정 생성
- **고객사 운영자 지정** — `POST /api/v1/owner/admins`(소유자만, `companyId`+`phone`[+`name`]), `companyId:null`이면 해제. 고객사 목록에서 "운영자 지정" 링크(`/owner/admins?companyId=`)로 그 고객사가 미리 선택됨
- **공용 로직 `lib/account-assign.ts`** — 소유자·(다른 등급) 계정은 못 바꿈, 다른 고객사 매장의 관리자를 가로채지 못함, **새로 만들 때는 임의 임시 비밀번호를 발급해 응답으로 한 번만 돌려줌**(권한 계정의 비밀번호는 로그인 화면에 공개하지 않는다. 새 사람은 문자 인증이 없어 스스로 가입할 수 없으므로 지정하면서 계정을 만든다)
- **UI** — `/owner/admins`(고객사 운영자 지정: 이름 칸, 임시 비밀번호 표시), `/hq/stores` → "매장·관리자"(매장 등록 + 매장별 관리자 목록·지정·해제)

### 논리 검토에서 찾아 바로 고친 것
1. **권한 해제가 최대 7일 뒤에야 반영되던 문제** — 세션(JWT)에 역할이 들어 있어 운영자·매장 관리자를 해제하거나 매장을 옮겨도 예전 권한이 남았다. `lib/session.ts`의 `getFreshSession()`이 권한 계정(owner/admin/manager)은 **요청마다 DB의 현재 역할·소속으로 다시 확인**하고, `requireSession()`(모든 권한 API)과 관리모드 레이아웃·진입 라우트가 이를 쓴다. 일반 고객은 DB를 보지 않는다(승격은 재로그인 후 반영 — 안전한 방향)
2. **권한 계정에 빈 비밀번호가 생길 수 있던 경로** — 손님 계정에 빈 비밀번호를 두던 방식을 없애고(5-3) 모든 계정이 항상 비밀번호를 갖도록 했다. 권한 계정의 초기·임시 비밀번호는 로그인 화면에 공개하지 않는다
3. 매장 생성이 관리자 신규 계정 생성을 강제해 "관리자 없이 매장 정보만" 상태를 만들 수 없던 문제 / 소유자의 운영자 지정이 기존 회원만 가능하던 문제

### 검토에서 발견한 것 — 통합포인트 고객사 분리는 **5-7에서 해결됨**
- ~~통합포인트가 고객사별로 나뉘지 않는다~~ → 5-7
- ~~`/hq/customers`, `/hq/points`, `usage`가 고객사와 무관하게 전체 고객 대상~~ → 5-7(현재 고객사 범위로 제한)
- 소유자가 매장 관리모드에서 한 결제·적립은 감사로그에 소유자 ID로 남고 "대신 처리" 표시는 없다(미해결)

### 운영 계정 정리 스크립트 `scripts/setup-accounts.ts` (작성만, 실행은 운영 서버에서 사람이)
실행 순서: `migrate-to-multitenant.ts` → `issue-initial-passwords.ts` → **`setup-accounts.ts`**(각각 미리보기 → `--apply`). 비밀번호는 저장소에 넣지 않고 `FIXED_PASSWORD` 환경변수로만 받으며, 아래 **4개 계정에 모두 같은 값**이 설정된다(그 외 모든 계정은 앱이 임의 비밀번호를 부여).
1. `01035587496`: **이름이 "배병철"인지 확인**(다르면 아무것도 바꾸지 않고 중단 — 이 경우 번호를 사용자에게 다시 확인) → 본사(owner)로 변경, 비밀번호 설정
2. `01000000000`: 소유자로 생성(있으면 소유자로 바꾸고 비밀번호 재설정)
3. `01000000001` → "반들한식뷔페" 고객사의 **고객사 운영자**, 비밀번호 설정(계정이 없으면 만들지 않고 알림)
4. `01000000002` → "반들한식뷔페" 매장의 **매장 관리자**, 비밀번호 설정(계정이 없으면 만들지 않고 알림)
5. "더파티"/"더파티 시청점"에 묶인 계정은 **확인만 하고 수정하지 않음**(나오면 사람이 처리 방침 결정)

4개 계정은 `firstLogin=true`로 두어 첫 로그인 때 "비밀번호를 변경하세요" 안내가 한 번 나온다. **같은 비밀번호를 여러 권한 계정(소유자 포함)에 쓰고 예측하기 쉬운 값일 수 있으므로 로그인 후 바로 바꾸는 것을 권한다.**

## 5-7. 통합포인트를 고객사 단위로 분리

요구: 통합포인트는 고객사별로 나뉘어야 하고, 한 고객사의 매장들은 통합 운영된다. 고객은 고객사별로 포인트를 확인한다.

**원장 규칙(`lib/points.ts`)**
- `PointAccount`·`PointEvent`에 `companyId` 추가. 통합포인트(HQ) 계좌는 **(고객, 고객사)당 1개**, 매장 계좌는 (고객, 매장)당 1개(매장의 고객사를 함께 저장)
- 사용 가능 잔액(`getAvailableForStore`)과 차감(`debitAvailable`)은 **같은 고객사 안에서만** 합산: 이 매장 → 그 고객사의 통합포인트 → 같은 고객사의 다른 매장 순. 다른 고객사의 포인트는 절대 쓰지 않는다
- 원장에 손대는 모든 경로(수동 적립·체크아웃·구 벤더 동기화·에이전트 적립/사용·일괄 이전·이체)가 매장의 고객사를 먼저 구해 계좌·내역에 채운다. 이체(`transferPoints`)는 다른 고객사 매장 포인트를 옮겨 올 수 없다
- `getMyPointSummary`는 이제 `{ companies: [...] }`(고객사별 통합포인트 지급분·매장별 잔액·합계). 한 고객사 안의 요약은 `getCompanyPointSummary`, 그 고객사에서 이용한 적이 있는지는 `hasCompanyRelation`
- 통합포인트 지급·조정(`grantHqPoints`/`adjustHqPoints`)은 `companyId`를 받는다

**화면·API**
- 고객 `/me`: **고객사별 카드**(고객사 이름 + 사용 가능한 통합포인트, 통합포인트 지급분·매장별 적립). 이용 내역에는 `고객사 · 매장/통합포인트` 표시. 전체 합계는 보여주지 않는다(다른 고객사끼리 합칠 수 없으므로)
- 고객사 관리모드(`/hq`): 고객 조회·이용내역·통합포인트 지급/조정 API가 **현재 고객사 범위**(`resolveCompanyId`). 고객 조회·이용내역·조정은 **그 고객사에서 이용한 적이 있는 고객만**(없으면 존재 여부도 알리지 않고 404). 지급은 가입한 고객이면 누구에게나 가능(신규 고객에게 미리 지급하는 용도). 소유자는 들어가 있는 고객사 기준
- POS 조회(`pos/customers/*`)는 그 매장이 속한 고객사 안의 잔액만 돌려준다
- 용어: 남아 있던 "본사 포인트/매장 포인트"를 "통합포인트"로 정리

**⚠ 마이그레이션 `scripts/migrate-company-points.ts`(작성만, 운영 서버에서 사람이) — 새 앱 시작 전에 실행**
1. 매장 계좌·내역에 매장의 고객사를 채운다
2. 기존 통합포인트 계좌는 어느 고객사 것인지 알 수 없다 — **잔액이 0이 아닌 계좌가 있으면 `--assign-hq-to="고객사 이름"`이 필수**(미리보기가 개수·합계를 알려준다). 잔액 0인 옛 계좌는 삭제(필요하면 앱이 다시 만든다)
3. 옛 유니크 인덱스 `userId_1_storeId_1_type_1`을 지우고 새 인덱스 생성. **이 인덱스가 남아 있으면 두 번째 고객사의 통합포인트 계좌를 만들 수 없다**
- `migrate-to-multitenant.ts`(고객사·매장 소속)를 먼저 실행한 뒤에 돌릴 것. 미리보기 → `--apply`, 기본은 미리보기

## 5-8. 고객사·매장 등록 신청 기능 점검과 수정

**점검 결과: 구현은 되어 있었으나 결함이 있어 고쳤다.** 있는 것: 공개 신청 화면 `/store-signup`, `POST /api/v1/store-applications`, `StoreApplication` 모델, 소유자 승인/반려(`/api/v1/hq/store-applications/[id]/approve|reject`), 소유자 화면 `/owner/applications`.
- **승인하면 항상 새 고객사를 만들었다** → 기존 고객사의 2호점 신청도 같은 이름의 고객사가 중복 생성됐다. 이제 승인 때 소유자가 **새 고객사로 만들지 / 기존 고객사에 추가할지** 고른다(신청자가 적은 이름과 같은 기존 고객사가 있으면 기본 선택). 같은 이름이 있는데 새로 만들려 하면 409(`COMPANY_NAME_EXISTS`)
- 소유자 목록에 매장명만 나오고 **고객사 이름이 없었다** → 신청한 고객사 이름과 신청 종류(새 고객사 / 기존 고객사에 추가) 표시
- 신청 종류가 없었다 → `type: NEW_COMPANY | ADD_STORE`(공개 화면에서 선택)
- **공개 API에 요청 횟수 제한이 없었다** → IP당 5회/시간. 전화번호 정규화·입력 길이 제한·비밀번호 규칙(8자) 서버 검증 추가
- 화면 이름 "매장 가입 신청" → "고객사·매장 등록 신청"
- **남은 한계(미해결):** 신청자에게 승인/반려가 자동 통지되지 않는다(문자 없음) — 화면에 안내 문구만 있다 / 이미 가입된 번호로는 신청할 수 없다(POS로 만들어진 손님 계정과 같은 번호면 막힘) / 승인된 신청자는 항상 **매장 관리자**가 된다(고객사 운영자는 승인 후 소유자가 따로 지정)

## 5-9. 관리모드 메뉴 순서·모드 전환 정리

- 모드 전환 링크를 `app/components/modeLinks.ts`로 통일: 라벨 **본사 관리모드 / 고객사 관리모드 / 매장 관리모드 / 고객 모드**, 순서는 권한이 높은 순(소유자 → 본사 → 매장 → 고객), 현재 모드는 제외. (기존엔 "회원 모드로/소유자 모드로/운영자 모드/매장 관리 모드"가 섞여 있고 위치도 화면마다 달랐다.) 소유자는 고객사를 골라 고객사 관리모드에 들어가는 게 원칙이라 매장 화면에서만 "고객사 관리모드" 링크를 둔다
- 사이드바 항목을 업무 흐름 순서로 재배치
  - 본사(소유자): 고객사 관리 → 고객사·매장 등록 신청 → 고객사 운영자 지정 → 고객앱 버전 관리
  - 고객사(운영자): 대시보드 → 매장·관리자 → 벤더 API 설정 → 고객 조회 → 통합포인트 관리 (매장 구성 → 고객 순)
  - 매장: 대시보드 → POS 결제 터미널 → 일일 정산 → 가입 안내 QR → POS 연동 동의 → 포스기 다운로드 → 연동 활동 로그 (일상 운영 → 고객 가입 → 연동 설정(동의 → 설치) → 로그)
  - 고객: 내 포인트 → 이용 내역 → 비밀번호 변경
- 사이드바 역할 표시: 본사 / 고객사 / 매장 / 고객

## 5-10. 용어 체계 재정리 (본사·고객사·매장·고객)

요구: 용어와 개념을 **본사(소유자) · 고객사(운영자) · 매장(관리자) · 고객**으로 다시 정리해 프로그램과 홈페이지에 반영. 계정 `role`(owner/admin/manager/user)은 그대로.
- **화면 문구 전수 정리** — 관리모드 이름(본사/고객사/매장/고객), 사이드바 상단 역할 표시(본사·고객사·매장·고객), 화면 머리말(eyebrow)·설명·오류 문구·확인창·상단 표시줄 안내, 고객사 운영자 지정/매장·고객사 등록 신청 화면, 로그인 화면의 등록 신청 링크("고객사·매장 등록 신청")
- 뒤바뀐 의미 정정: 고객사 관리모드 화면 머리말은 `고객사 관리모드`(본사가 들어오면 `본사 · 고객사 관리모드`), 사이드바 "본사 운영자 지정" → "고객사 운영자 지정", 정산 화면의 "웹/본사" → "웹/관리모드", 앱 설명 문구를 "고객사별 통합포인트…"로
- 코드 주석·정의(`lib/models/User.ts` 등급 설명, `lib/rbac.ts`, `lib/company-context.ts`, `lib/points.ts`, `lib/account-assign.ts`)와 스크립트 안내문을 같은 용어로 맞춤. **함수·변수·경로 이름은 그대로**(예: `requireOwner`=본사, `requireCompanyAdmin`=고객사 이상, `requireStoreManager`=매장 이상)
- "회원가입"(가입 동작을 뜻하는 일반 표현)은 그대로 두고, 계정 종류를 가리키던 "회원"은 "고객"으로

## 5-11. 본사 대표 안내문 검증과 보완 (포스기 설치·대표 포스기·계정)

안내문 각 항목을 코드와 대조했다. **맞는 것:** 계정 4개 구성(본사 3개 권한 = `owner`가 고객사·매장 관리모드 전부 사용 가능, 테스트 계정 3개, 같은 비밀번호, 첫 로그인 변경 안내), 매장 계정으로 로그인해 "포스기 다운로드" → zip → `start.bat` → 등록·초기화, 첫 포스기가 대표 포스기.

**안내문과 다르게 동작하는 부분(안내문을 고치는 편이 맞다):**
- **"바탕화면에 프로그램 설치"는 사실과 다르다.** 프로그램은 별도 설치 없이 **압축을 푼 폴더에서 그대로 실행**된다(설정 `terminal-config.json`·`bulk-import-done.json`도 그 폴더에 저장, 로그온 자동시작 작업도 그 폴더의 스크립트를 가리킨다). 바탕화면에 만들어지는 것은 **대표 포스기의 "포인트 관리모드" 바로가기 하나**뿐이다. → 압축을 푼 폴더를 지우거나 옮기면 자동시작이 깨지므로 **삭제 금지 폴더에 풀도록** 안내해야 한다
- **"나머지 포스기는 적립·사용만"** 은 바로가기가 대표에게만 생긴다는 뜻이다. 웹 관리모드는 **어느 PC에서든 매장 계정으로 로그인하면 열린다**(서버가 대표 포스기에서만 열리게 막지는 않는다)
- 다운로드한 zip은 **한 번만 등록**된다(24시간 유효). 포스기마다 그 PC에서 따로 받아야 하고, **같은 PC에서 다시 받아 다른 폴더에서 실행하면 새 포스기로 중복 등록**된다(이전 것은 포스기 목록에서 "해지")
- Chrome으로 받은 zip은 Windows 보호 기능(SmartScreen / 인터넷에서 받은 파일 차단)이 `start.bat` 실행을 막을 수 있다 — "추가 정보 → 실행" 또는 zip 우클릭 → 속성 → **차단 해제** 후 압축 풀기(코드로 확인한 것이 아니라 Windows 일반 동작)

**이번에 고친 것**
- **대표 포스기 선정**: 예전에는 활성 포스기가 0대일 때만 대표가 되어, **대표를 해지한 뒤 새로 등록해도 대표가 다시 생기지 않았다.** 이제 "사용 중인 대표가 없으면" 대표가 된다(`/api/v1/pos/agent/register`)
- **대표 포스기 바로가기(`/store`) → 로그인 → 매장 관리모드**: 로그인 후 항상 `/me`로 가서 관리모드가 바로 열리지 않았다. 이제 `/login?next=/store`(고객사·본사 관리모드 화면도 동일)로 보내고, 로그인 뒤 그 화면으로 이동한다. `next`는 같은 사이트 내부 경로(`/영문·숫자·-_/`)만 허용(외부 주소 리다이렉트 방지). 초기 비밀번호 첫 로그인이면 변경 안내가 우선

**확인하지 못한 것**: PowerShell(`point-terminal-agent.ps1`)은 클라우드에서 실행할 수 없어 코드로만 확인했다(실기기 테스트는 사용자가 진행). 대표 포스기 바탕화면 바로가기는 `iexplore.exe`가 없으면 URL을 `.lnk` 대상으로 지정하는데, 최신 Windows에서 정상 동작하는지는 실기기 확인이 필요하다.

## 5-12. 신규 자가가입: 문자 인증 없이 폰번호·비밀번호로 바로 가입

요구: 문자 인증이 없으므로, 입력한 휴대폰번호와 비밀번호로 그냥 가입시킨다. 신원 확인은 나중에 매장에서 결제할 때 기록되는 카드 식별번호와 전화번호로 한다(고객 확인은 결국 전화번호로 진행).

- `POST /api/v1/auth/customer/signup` — 번호 정규화(숫자만)·이름·비밀번호(8자 이상) 검증 후 **User를 즉시 생성**하고 로그인 세션 발급(`phoneVerified=false`). IP당 5회/10분 제한, 같은 번호 동시 가입은 유니크 인덱스 충돌로 막는다(`PHONE_ALREADY_USED`). 매장 QR 유입(`storeRef`)은 형식 검증 후 참고용으로만 기록
- `/signup` 화면: 인증번호 단계를 없애고 가입 즉시 `/me`(영수증 QR로 들어왔다면 카드 연결 화면)로 이동
- **삭제:** `POST /api/v1/auth/otp/verify`, `lib/models/PendingCustomerSignup.ts`(가입 대기 컬렉션은 더 쓰이지 않는다 — DB에 남은 문서는 TTL로 사라지고 정리할 필요 없음). `lib/otp.ts`는 비밀번호 찾기가 계속 사용
- 이미 매장(POS)에서 만들어진 번호는 여전히 가입되지 않는다(`PHONE_ALREADY_USED`) — 그 손님은 로그인 화면의 "처음 로그인하시나요? 초기 비밀번호 확인"을 쓴다(5-3)

**⚠ 알려진 한계 (요청에 따라 수용)**
- **아직 어떤 계정도 없는 번호는 누구든 먼저 가입할 수 있다.** 나중에 진짜 주인이 그 번호로 매장에서 적립하면 포인트가 먼저 가입한 사람의 계정에 쌓인다(계산원은 전화번호로 고객을 확인하므로). 카드 식별번호는 결제 기록(`PointEvent.cardNo`)에 남지만 **현재는 인증 수단으로 쓰이지 않는다**(카드는 빌려 쓸 수 있다는 기존 설계). 필요하면 후속으로 "카운터에서 본인 확인 후 비밀번호 재발급(매장 관리자)"을 추가할 것
- 비밀번호를 바꿔도 다른 기기의 기존 로그인은 유지된다(세션 7일)

## 6. 검증 못 한 것 / 알려진 한계

- **PowerShell 스크립트는 실행해 보지 못했다**(클라우드에 `pwsh` 없음). 코드 리뷰로만 확인. 실기기 테스트 필요
- DB 접근이 없어 마이그레이션·토큰 등록·비밀번호 재설정 흐름은 모두 미실행. **웹 푸시도 실제 기기로 발송해 보지 못했다**(엔드포인트 허용 목록 로직만 단독 테스트)
- `npm audit`에 취약점 5건(critical 1, high 3, moderate 1)이 보이지만 `web-push` 추가 전에도 같았다(기존 의존성). 이 변경과 무관
- 세션이 JWT(7일)라 비밀번호를 바꿔도 **다른 기기의 기존 로그인은 유지된다**. 강제 로그아웃이 필요하면 `passwordChangedAt` 필드를 두고 세션 검증에서 비교하는 방식을 추가해야 한다
- `app/store/consent/ConsentClient.tsx` 85행에 사용자 화면용 도메인 표기가 남아 있다(용어 규칙 위반, 기존 코드라 손대지 않음)
- 문서 밖 상태: `uploads/pos-agent/point-terminal-agent.zip`은 더 이상 쓰이지 않는다(삭제 가능)
